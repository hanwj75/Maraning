# Cursor Codex Workflow

## Working Principles

- 모든 구현 작업은 관련 문서 확인 또는 문서 갱신으로 시작한다.
- 문서가 없는 기능은 바로 구현하지 않고 먼저 문서 기준선을 만든다.
- 변경은 작은 단위로 나눈다.
- 테스트 없는 기능은 완료로 간주하지 않는다.
- 관련 없는 리팩토링은 하지 않는다.

## Document First Flow

1. 현재 작업 범위를 명확히 정의한다.
2. 관련 아키텍처, 데이터, UI, 품질 문서를 확인한다.
3. 필요한 문서가 비어 있거나 부족하면 먼저 문서를 작성 또는 수정한다.
4. 문서 기준이 합의된 뒤에만 구현 작업으로 이동한다.
5. 구현 후 테스트 문서와 changelog 를 함께 갱신한다.

## Task Unit Rules

- 한 번의 작업은 하나의 명확한 목적을 가져야 한다.
- 한 번에 여러 시스템을 동시에 크게 흔들지 않는다.
- 기능, 상태, 데이터, UI 변경은 가능한 한 분리된 단위로 다룬다.
- 문서와 테스트 영향 범위를 설명할 수 없는 변경은 줄이거나 나눈다.

## Document Update Flow

- 제품 흐름 변경 시 `docs/product/*` 를 먼저 갱신한다.
- 도메인 규칙 변경 시 `docs/architecture/*` 와 `docs/data/*` 를 함께 갱신한다.
- UI 변경 시 `docs/ui/*` 와 품질 기준을 함께 본다.
- 개발 방식 변경 시 `docs/development/*` 를 갱신한다.
- 완료 기준이나 검증 범위 변경 시 `docs/quality/*` 를 갱신한다.

## Implementation Handoff Rules

- 구현 전에는 참조 문서를 명시한다.
- 구현 후에는 어떤 문서와 어떤 테스트 기준이 갱신되었는지 남긴다.
- 문서 기준과 실제 구현이 다르면 구현만 고치지 말고 문서도 함께 정리한다.
- handoff 시 다음 작업자가 바로 이어서 볼 수 있게 남은 위험과 미결정 사항을 분명히 적는다.

## Change Control

- 작은 단위 변경을 기본값으로 한다.
- 한 변경은 하나의 사용자 가치 또는 하나의 시스템 규칙에 집중해야 한다.
- 테스트가 준비되지 않은 변경은 merge-ready 상태가 아니다.
- changelog 기록 없이 의미 있는 규칙 변경을 남기지 않는다.
